# Phase 5: E2E requirements (optional)

The rules and where each is proved are already in the approved spec: `## Business rules` › Rules lists the user-visible rules (`BR-<n>`) at one surface, and `## Testing` gives each its e2e env or the reason it is not e2e. This phase only adds the test cases.

## Gate B: e2e test plan?

Ask whether to add e2e requirements ([templates/asks.md › Gate asks](../templates/asks.md#gate-asks)). **No:** go to [phase 6](6-plan.md). When the spec already has an `## E2E requirements` section (update mode) and the spec changed, the question is whether to refresh it; a section left as it is may no longer match the spec, so say that in the ask.

## Write the section

1. Spawn the **Test planner**. It writes `<workdir>/e2e-section.md` in the shape of [templates/e2e.md](../templates/e2e.md#e2e-requirements-section).
2. Check it yourself: the rules table matches the spec's `## Business rules` › Rules row for row; every `BR-<n>` with an e2e env in `## Testing` has at least one case with that env; every rule under "Not provable by e2e" has its one line and no case; every case names its rule; no `<…>` slot is left.
3. Put the section into the spec: replace an existing `## E2E requirements` section, otherwise append it at the end. Change nothing else in the spec. `stamp` the spec.

## Gate C: the e2e section

Report the number of e2e rules and cases, the open questions, and the new `rev` and `hash`, then ask.

- **Changes to a case:** a fresh Test planner with the human's words as `CHANGES`; then steps 2 and 3 again.
- **Changes to a rule** (its wording, a missing rule, its env): that is a change to the approved spec. Resume the Spec writer with the human's words (as for gate A changes), `stamp`, ask gate A again, then a fresh Test planner and steps 2 and 3.
- **Drop the section:** delete it from the spec, `stamp`, and go to [phase 6](6-plan.md) without asking gate C again.
- **Yes:** [phase 6](6-plan.md).
