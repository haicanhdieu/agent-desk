# 0007. Drizzle for data access and migrations

- Status: Accepted
- Date: 2026-11-12
- Source: control plane design §2 (Data access), §4; infra design §6.3

## Context

The data layer has to express Postgres row-level security policies in the
schema ([0006](0006-tenant-ready-schema-with-rls.md)), set a per-transaction
tenant setting, use `SKIP LOCKED` and jsonb with types, and produce migrations
that a reviewer can read and that a Helm hook can run against in-cluster or
managed Postgres. better-auth needs an adapter for its own tables.

## Decision

Use Drizzle ORM and drizzle-kit in `packages/db`:

- Schema, RLS policies (`pgPolicy`), roles and the `SECURITY DEFINER`
  functions live in `packages/db`.
- Migrations are SQL files generated by drizzle-kit and run as
  `agentdesk_owner` by the api image's migrate entrypoint (a Helm
  `pre-install,pre-upgrade` hook in deployed targets).
- better-auth uses its Drizzle adapter for `user`, `session`, `account`,
  `organization`, `member` and `invitation`.

## Alternatives considered

| Alternative                                | Why rejected                                                                                                                                                |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Kysely, Prisma, MikroORM, TypeORM, raw SQL | Weighed; Drizzle chosen for RLS policies in the schema, typed `SKIP LOCKED` and jsonb, reviewable SQL migrations, and simple per-transaction tenant context |

The spec gives the reasons for Drizzle, not a separate rejection reason for each
alternative.

## Consequences

### Positive

- RLS policies are versioned with the tables they protect.
- Migrations are plain SQL, reviewable and runnable against RDS or Azure
  Postgres without init scripts.
- `withOrg` is a thin wrapper over a Drizzle transaction.

### Negative

- Open check: `pgPolicy` with `FORCE ROW LEVEL SECURITY` and definer functions
  through drizzle-kit migrations.
- Open check: `CREATE ROLE` rights of managed Postgres admin users for the
  migrate entrypoint.
